## 1. 审查方法与证据边界

本轮采用三路只读并行审查，再由主代理逐项复核：

1. **发布运维**：脚本、CI、Git、部署、在线验证、回滚、凭据边界和可恢复性。
2. **工程安全**：真实运行路径、测试覆盖、鉴权、限流、请求上限、错误处理、秘密处理和 MCP 契约。
3. **交付体验**：清单、版本、域名、二维码、媒体时长、字幕、双语切换、下载、证据标签和人工接受门。

每条结论只分为 `confirmed`、`inferred`、`unknown`。测试通过、文件存在和子代理报告都不单独作为完成证明；必须与当前文件、命令输出或真实浏览器/公网观察对应。

## 4. 确认风险与未完成项

- 最终审计辅助脚本已改为从当前清单、ZIP、Git 和在线证据推导，并以快照稳定性预检拒绝过期报告；实际报告仍须在最终构建与发布后重跑验收。
- 全量在线哈希验证已实现逐文件缓存、有界并发、批处理和失败保留；尚须在新部署后分批跑到 `hash_pending=0`。
- GitHub Pages 不执行 Pages Function，也不支持严格 HTTP 206；静态站点通过不能替代生产 Web MCP 通过。
- 生产 Web MCP 仍受 Cloudflare Access 阻塞，且真实环境缺少 `MI_MCP_PUBLIC_TOKEN`；只能报告本地运行时通过。
- `verify_site.py` 已新增 `--strict`：缺少 token、未启用 deep 或未执行生产限流探测时直接失败；无 token 的非严格模式只报告“静态检查通过”，不再输出“全部通过”。
- Meaning Agent 本地 MCP 与公开 Web MCP 是两套契约；协议版本、资源/工具集合和同名参数不可暗示自动兼容。
- SDK 仍可能输出缺乏证据支撑的 E1 占位或加权方向选择，需隔离或修正。
- Pages 多实例限流、生产密钥/CORS 行为和真实 Function 路径尚未验证。
- 人工无障碍、视觉、发音、权利和最终内容接受仍待评审。
- 正典上游仍有 H5 截断、H6 简表与卡片冲突、英文正文不足、图片占位等已知缺口；本轮没有静默改写原件。

## 5. 反思

### 有效做法

- 先保留正典和用户原件，再用衍生文档、补充材料修正传播层。
- 将二维码、PPT、手册、文档、下载页和 manifest 作为同一一致性单元重建。
- 区分本地包、部署集、源码包和完整 ZIP 的边界，避免自引用和超大文件泄漏。
- 用真实浏览器、媒体解码、哈希和协议测试替代“文件存在”式检查。
- 长任务逐文件保存结果，未完成批次保持显式 pending。

### 需要改进

- 审计脚本不应写死项目事实；应从参数、当前 manifest 和实时 Git 读取。
- CI 应直接校验实际部署入口，而不是只证明同步工具可用。
- 公开服务的滥用控制必须覆盖未认证流量。
- 媒体时间轴必须以实际编码时长为准，不能使用合成脚本的估计值。
- 源文件与发布副本必须做字节或内容级核对，尤其关注二维码和二进制。
- 机器全绿不能替代人工门；完成声明必须逐项映射原需求。
- 项目专属知识留在 reference，通用流程、检查门和提示词留在可迁移 Skill。
