# 意义智能项目维护

## 目标与触发

维护正典/工程边界、构建 MSI 或白皮书、运行仓库校验、检查发布包时使用本 Skill。它提供确定性审计脚本和按需加载的来源手册，不替代正典。

## 不可突破的规则

- 将六层栈、三带和 MSI 声明为 **E0 工程扩展**，不得称为 V7.0 正典固定层次。正典原 L1–L3 与工程 L1–L6 不是同一编号系统。
- 理论定义、E0–E6、H1–H18 和附录 D.7 以 V7.0 正典为准；冲突时记录冲突，不静默改写正典。
- 将“本框架操作化”“正典假设”“外部机制”分别评级。外部机制等级不得转移给工程层。
- 将工程证伪草案先预注册，再用于正式处置；未预注册的观察只能指导探索。
- 不读取 token、密钥或凭据文件，不打印环境变量或秘密。
- 无明确授权，不 commit/push、不部署、不删除、不修改共享配置。构建不等于发布授权。

## 工作流程

### 1. 定位并分类来源

从仓库根开始，读取 `references/provenance.md`。先确认任务对象属于正典、白皮书、MSI 工程实现还是传播材料，再决定修改入口。版本号只认 `VERSION.yaml`。

- 理论表述：对照正典、`hypotheses.yaml` 与 `docs/`；不要从 README 反推正典。
- MSI 文案：从 `msi/config.json` 入手；场景与页面共用其数据。
- 白皮书：改 `whitepaper/build_whitepaper.py`，不手改 DOCX。
- 证伪：先判定对象与范围，再按 `docs/failure-matrix.md` 和 `docs/equivalence-tests.md` 处理。

### 2. 维护边界与证据

修改任何层名、定义、证据等级、H 映射或证伪条件前，对照手册中的六层表逐项检查。保持“概念关联”与“层定义”分离，保持“工程草案”与“正典阈值”分离。若用户未授权修改其他文件，只提出差异，不越权修复。

### 3. 构建与校验

优先运行审计脚本，不要自行重排步骤：

```bash
python .qoder/skills/meaning-intelligence-maintain/scripts/audit.py
```

该命令从自身路径定位仓库根，不依赖当前工作目录；默认只审计。仅在用户要求重建白皮书时追加：

```bash
python .qoder/skills/meaning-intelligence-maintain/scripts/audit.py --build-whitepaper
```

构建会重写 MSI HTML/图表；白皮书选项还会重写插图与 `whitepaper/dist/` 中的 DOCX。运行前告知这些生成物会变化。每个子命令使用参数数组启动，不经过 shell；任何失败立即打印退出码、停止后续步骤并传播非零状态。

若 `verify_consistency.py` 因其他代理正在编辑白皮书而暂时失败，如实报告文件名与失败步骤，等待源文件稳定后重跑。不得改校验器、证据文案或其他文件来绕过失败。

### 4. 检查发布包

按手册中的清单核对文件名、版本、DOCX 结构、PDF 可读性、页面资源与时间轴来源。只构建和检查，不调用发布工具、不读取凭据、不部署。

## 交付要求

- 汇报改动文件、执行的命令、各步骤结果和仍存在的阻塞。
- 将“通过”“跳过”“失败”明确分开；Node 缺失导致的 JS 语法跳过不得写成通过。
- 对理论等级或处置的每次变更，说明对象、依据与是否涉及正式预注册阈值。
- 未完成授权动作时明确说明“未执行”。

## 资源

- `references/provenance.md`：权威顺序、E0–E6 精确定义、六层证据与 H 映射、正式处置规则、构建命令和发布包清单。需要细节时加载。
