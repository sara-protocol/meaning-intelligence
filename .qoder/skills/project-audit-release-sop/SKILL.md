# 项目审查与发布 SOP

## 用途

把一次性的项目经验固化为可重复、可审计、可回滚的交付流程。适用于代码、文档、PPT、电子书、音视频、静态站点和 Web 服务组成的混合项目。

## 先建立项目配置

开始前在对话中确认以下变量；未知项标为 `unknown`，不得猜测：

```text
<PROJECT_ROOT>              仓库或工作区根目录
<AUTHORITATIVE_SOURCES>     正典、需求、设计、数据及其优先级
<DELIVERABLES>             必须交付的具名文件、页面、媒体或服务
<VERSION_SOURCE>            版本与日期的唯一来源
<BUILD_COMMANDS>            构建、测试、静态检查命令
<RELEASE_TARGETS>           已授权的仓库、站点或发布渠道
<FORBIDDEN_ACTIONS>         删除、强推、共享配置、权限、DNS 等禁止项
<HUMAN_GATES>               内容、权利、无障碍、安全、实证验证等人工门
<EVIDENCE_DIR>              审计日志与验收报告输出目录
```

若未提供发布目标或授权，只构建、检查和打包，不 commit、push、部署或修改共享状态。

## 不可突破规则

- 当前工作区、当前文件和刚产生的命令输出是事实依据；历史总结只用于定位。
- 每个“通过”必须对应命令、测试、文件、日志或可复现观察；未执行、跳过、超时、环境阻塞都不能写成通过。
- 正典、用户原件和权威来源默认只读；冲突记录为 errata 或补充，不静默改写。
- 构建、检查、发布是三个阶段。检查通过不等于获得发布授权。
- 不读取、打印、持久化或提交 token、密钥、凭据；只报告存在或缺失。
- 不使用强推、破坏性恢复、跳过钩子、降低验收标准来制造绿色状态。
- 外部写操作仅限明确授权的目标与范围；授权一次不代表永久授权。
- 验证器不得写死项目路径、域名、版本、计数、哈希或提交；从当前清单和实时状态推导。
- 网络请求、子进程和浏览器操作必须有超时；长任务逐项保存结果并支持续跑。
- 按发布平台建立能力档案，分别验证 Function、Range、Access、缓存和构建行为。
- 将“功能通过”“严格协议通过”“人工接受”分开记录。
- 公开服务的限流与请求成本控制必须覆盖未认证请求；鉴权不能成为绕过配额的入口。
- CI 必须校验实际部署文件的字节身份，不能只验证临时副本或生成脚本。
- 同名 API/MCP 工具若协议或参数不同，必须分别登记契约，禁止暗示自动兼容。
- 媒体时间轴以实际编码时长为准；字幕尾部不得超出音频，源文件与发布副本必须逐字节或逐内容核对。
- 严格完成模式把 `skipped`、`blocked`、`pending-human` 视为未完成，不输出“全部通过”。

## 工作流程

### 0. 需求接入与基线

读取需求、仓库状态、版本来源、现有清单和最近证据。建立提示词到交付物 checklist，记录基线提交、文件哈希、依赖和未提交改动。先确认是否允许修改。

### 1. 并行审查

按领域拆分互不重叠的只读审查任务，每条提示词必须指定范围、禁止动作、证据格式和输出上限。至少覆盖：

- 交付物：清单、版本、域名、链接、媒体时长、字幕、双语切换、下载。
- 工程：构建、测试、运行路径、安全边界、秘密处理、失败行为。
- 发布运维：脚本、CI、Git、部署、在线验证、回滚、可恢复性。
- 内容与体验：正典边界、权利、无障碍、移动端、 pronunciation 与人工评审。

主代理汇总结果，不重复子代理已完成的搜索。区分 `confirmed`、`inferred`、`unknown`。

### 2. 反思与排序

把发现归类为：正确性、一致性、安全性、可维护性、可恢复性、用户体验、权利与证据。按“影响 × 证据强度 × 修复成本”排序。每次反思回答：

- 哪些做法真正降低了风险？
- 哪些绿色检查覆盖不了真实需求？
- 哪些手工重复步骤应脚本化？
- 哪些项目专属知识应留在 reference，而非硬编码？
- 下一次应在哪个更早的门失败？

### 3. 计划与修复

先写最小完整计划，再修改来源，不手改可再生成产物。一次只修一类问题；每项修复绑定验收命令和预期证据。涉及生成物时，先改生成器，再完整重建，最后刷新清单与哈希。

### 4. 本地验收

按依赖顺序运行构建、单元/集成测试、静态检查、真实浏览器交互、媒体解码和包完整性检查。失败时保留日志，修复根因后重跑受影响门；不重写校验器来适应错误产物。

### 5. 发布前门

核对 staged diff、秘密、临时文件、版本、链接、下载、媒体和回滚点。取得所需人工批准。只有全部必需门通过，才进入发布。

### 6. 发布与在线验收

使用已授权渠道，优先非强制、可回滚发布。发布后从公网重新检查首页、关键交互、下载、媒体流、API/MCP、HTTPS、缓存和错误页。本地或 staging 通过不能替代在线证据。

### 7. 复盘与 Skill 更新

记录发布标识、实测结果、偏差、人工待办和回滚方法。把可泛化经验提炼为规则、检查门或提示词；项目专属路径与事实留在项目 reference。

## 交付格式

每次任务至少输出：

```text
结论：完成 / 部分完成 / 阻塞
需求到证据 checklist
已修改文件与生成物
执行命令及结果
确认问题、推断风险、未知项
发布动作与授权范围
人工评审待办
下一步与回滚入口
```

## 自校验

```bash
python scripts/validate_skill.py
```

该命令从脚本位置定位 Skill 目录，不依赖当前工作目录。校验通过只证明 Skill 结构完整，不证明目标项目已经通过验收。
